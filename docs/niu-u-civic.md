# 小牛u中控与总线协议研究

## 总结
记录了对小牛u civic电动车的总线通信的分析过程，希望可以对故障诊断和维修有帮助。

## 前言
咸鱼400元买了个二手小牛u1，卖家说刹车坏了车开不了，本想着可能只是断电开关坏了想捡漏，结果翻车。更像是霍尔传感器故障，拧转把后轮咯噔几下车不走，这我就不知道咋办了。后来推车推了一半又启动了下，居然好了开回家了。后面又反复了几次，把座桶拆下来插拔了下线，居然再没犯过了。估计问题还在，虚接之类，只是现在恰好搭上了。

小牛早期型号的俗称比较混乱，光一个“小牛u1”并不能知道到底是哪辆车。我这个车车标是“Ucivic”，应该是很早期的型号，中控上写着“2017.08”，所以车大概也是2017年的，到2025算算都8年老车了。

之前自己的爱玛AM1坏了无法开机，白嫖老板知识产权自己换了个报警器好了。其间学习了一点电动车的知识。然后搜了搜小牛电动车的电路原理图，发现还挺复杂。这里记录一些发现。

小牛算是电动车智能的先行者，就是车本身可以联网，不需要通过用户手机转发。这是通过“中控”实现的，里面有2G模块和GPS模块，还连接到车身总线上作为主控控制其他部件。而最简单的实体钥匙开机的电动车，基本就是只有个控制器控制电机，仪表显示下电池电压，连速度显示都没有。稍微复杂些的带无线钥匙的如我的爱玛AM1，多了个报警器，可以用无线钥匙开锁，仪表和控制器通信显示下挡位速度。

u1总线是个485总线，总线上连着这几个部件：中控，仪表，电池，电机控制器。485算是串口的一种，是个半双工总线。一般跑在485总线上的协议会类似modbus，总体看是比较简单的，就是总是中控发起通信，不断轮询所有的部件，收集和发送信息。开车的时候，每一个循环大概就是4步：询问电池电量，询问电机控制器速度和挡位，结合中控自身的信息，发送到仪表显示内容。

既然是485总线，我们就可以花上5块钱买个usb转485模块，插电脑上监听下车的启动和运行时的通信，然后把485A和485B分连在充电口上面左边起两个孔就可以。启动时会初始化，初始化完全之后就是轮询把信息显示到仪表上。

参考了另外两篇文章，描述的还是非常准确的，可以先看看：
* [小牛电池协议逆向](https://zhuanlan.zhihu.com/p/419857440) 
* [关于小牛V35中控专用协议总结](https://zhuanlan.zhihu.com/p/1697817972)

写了个python脚本`serial_logger.py`，监听串口的所有通信，按照收到通信的时间保存到文件里，每行格式如“时间点：字节流”，字节都是16进制。这里来分析一下。有个对应的操作视频，这样可以知道什么操作下收发了什么通信帧。

脚本和抓到的数据都在github: https://github.com/xzfn/scooter-repair

## 帧格式

帧的基本格式如下：

|0 |1   |      2|3 |4   |5    |6...    |-2    |-1|
|- |-   |      -|- |-   |-    |-       |-     |- |
|68|地址|地址反码|68|功能|字节数|帧内容...|校验和|16|

“帧内容”需要减掉0x33才是实际的数据，但是计算校验和用原始数据。

这里以打开中控后第一个通信为例重新描述下帧的格式。

```
9.538928747177124   : 68 31 ce 68 02 02 60 42 75 16
9.570258140563965   : 68 31 ce 68 82 0f 35 4c 33 33 33 35 97 33 34 33 4c 4c 4c 4c 4c 5c 16
```

例如`68 31 ce 68 02 02 60 42 75 16`

```python
# [0]68: 起始一个0x68
# [1]31: 0x31是地址，这里代表电池
>>> hex(~0x31 & 0xff)
'0xce'
# [2]ce: 0x31的反码是0xce
# [3]68: 帧头结尾一个0x68

# [4]02: 代表功能
# [5]02: 代表字节数，两个字节

# [6...]60 42: 2个字节内容

# [-2]75: 校验和，从最开头一直累加到帧内容最后一个字节
>>> sum(bytes.fromhex('68 31 ce 68 02 02 60 42'))
629
>>> hex(629 & 0xff)
'0x75'
# 这个帧的校验和是0x75

# [-1]16: 最后有个0x16结尾
```

再看下电池BMS的回复`68 31 ce 68 82 0f 35 4c 33 33 33 35 97 33 34 33 4c 4c 4c 4c 4c 5c 16`

```python
# [0]68: 起始一个0x68
# [1]31: 0x31是地址，这里代表电池
>>> hex(~0x31 & 0xff)
'0xce'
# [2]ce: 0x31的反码是0xce
# [3]68: 帧头结尾一个0x68

# [4]82: 代表功能，这里最高位是1代表回复
# [5]0f: 代表字节数，15个字节

# [6...]35 4c 33 33 33 35 97 33 34 33 4c 4c 4c 4c 4c: 15个字节内容

# [-2]5c: 校验和，从最开头一直累加到帧内容最后一个字节
>>> sum(bytes.fromhex('68 31 ce 68 82 0f 35 4c 33 33 33 35 97 33 34 33 4c 4c 4c 4c 4c'))
1628
>>> hex(1628 & 0xff)
'0x5c'
# 这个帧的校验和是0x5c

# [-1]16: 最后有个0x16结尾
```

实际使用的帧内容，需要每个字节减去0x33，例如第一个帧的原始帧内容是`60 42`，那实际的数据的计算如下
```python
>>> hex((0x60 - 0x33) & 0xff)
'0x2d'
>>> hex((0x42 - 0x33) & 0xff)
'0xf'
```
所以`60 42`对应的实际数据是`2d 0f`。

## 初步分析
智能带来了便捷，但是故障点也会变多。我买了这个小牛，搜了搜网上的一些故障信息，理解了经典轩逸的含金量。例如中控，电池，通信总线（大线），任何一个故障都可能导致无法显示速度，无法显示电量，无法切换挡位等问题。

上面提到我把中控电池拔了并且加了个手动开关，这样可以进行一些实验。个人认为一个niu车能用和不能用，最主要的是能否正常切换挡位。

有不同的故障都会造成无法切换挡位。一个重要的实验如下：

1. 关闭中控电源，车辆上电，只能一挡慢慢骑，无法切换挡位，仪表无显示；
2. 这时打开中控电源，稍等一会，就可以切换挡位了，仪表也有显示了；
3. 这时再关闭中控电源，仍然可以切换挡位，仪表无显示。

从网上也可以看到，如果用了非原装电池，或者说不带小牛通信协议的电池，会报故障码，并且锁一挡，并且仪表不显示电量。

所以我认为上电过程中，中控会判断是否能和电池通信，如果可以的话，告诉电机控制器“可以解锁挡位”，这时按挡位按钮，电机控制器才会切换挡位。挡位按钮是直接接在电机控制器上的，没有经过中控。

所以如果小牛车无法切换挡位，又出了保修不想去牛店随随便便花个三五百换中控，电池，电机控制器，大线啥的，需要咋操作呢？首先可以去咸鱼收二手，但是首先可以理论分析下非牛配件的可能性：

* 如果中控彻底坏了，可以外接一个简单的485模块，开机时给电机控制器发送“解锁挡位”。这样车可以正常骑但是仪表无显示。而且可以随便换第三方电池。外接个电压电量表可以接受。也可以买个接相线的速度表显示速度。
* 如果中控彻底坏了，可以外接一个复杂的485模块，除了发送解锁挡位，这样可以像真正的中控那样从电池和电机控制器收集信息，再显示到仪表上。但是这样没有联网，也没有时间（时间是通过GPS获得的）。
* 如果电池通信坏了，或者换了第三方电池，可以外接一个简单的485模块，假装自己是电池，接受中控的查询。这样中控以为有正常电池，会让电机控制器解锁挡位。如果这个模块额外输入电池电压，可以从电压估算电量，传给中控，这样电量也可以显示了，只是从电压估计肯定不如原装的准，除非新电池有另外的协议，这样可以转成小牛电池的协议，电量会非常准。

感觉最彻底的还是第一个方案，这样只要电机控制器是好的，仪表、中控、电池都可以出咸鱼回血，车也可以正常开。其实这些东西早就有人想到并且付诸实践了，可以在淘宝上搜到各种兼容模块，甚至兼容的BMS。

## 轮询帧分析

开机后，初始化完成之后，进入了一个不断的轮询。其本质就是中控把收集的信息显示到仪表上。

```
60.78084349632263   : (->BMS) 31 02 2d 0f
60.812402963638306  : (<-BMS) 31 82 02 19 00 00 00 01 64 00 00 00 19 19 19 19 19
60.97992992401123   : (->FOC) 20 02 05 08
61.011497259140015  : (<-FOC) 20 82 30 26 3c 01 00 16 00 00 00 00 08 00
61.0958685874939    : (->Dash) 10 04 06 f0 01 00 27 2e 00 00 00 00 64 00 cc cc 00
61.13853454589844   : (<-Dash) 10 84 01
```

BMS返回的主要是电量，我的是100%，就是0x64。怀疑格式是这样的：

|0,1|2-4|5|6|7,8,9|10-15|
|-|-|-|-|-|-|
|02 19|00 00 00|01|64|00 00 00|19 19 19 19 19|
|电压|未知|电流|电量|未知|温度|

```
# [0,1]02 19: 电压53.7伏
>>> 0x0219
537
# [5]01: 电流1A
# [6]64: 电量100%
>>> 0x64
100
# [10-15]19: 温度25度
>>> 0x19
25
```

FOC返回主要是速度和挡位。格式怀疑是这样的：

|0-8|9|10,11|
|-|-|-|
|未知|速度|未知|
|30 26 3c 01 00 16 00 00 00|00|08 00|

Dash就是显示各种信息了。格式从《关于小牛V35中控专用协议总结》中看是这样的：

|0|1|2|3|4-6|7-9|10|11|12,13|14|
|-|-|-|-|-|-|-|-|-|-|
|标志|标志|运动模式|速度|行驶里程|00 00 00|当前电量|00|时间|00|
|06|f0|01|00|27 2e 00|00 00 00|64|00|cc cc|00|

```
# [3]00: 速度为0
# [4-6]27 2e 00: 行驶里程，little endian
>>> 0x002e27
11815
# [10]64: 当前电量100%
>>> 0x64
100
# [12,13]cc cc: 当前时间，GPS尚未获取到时间为0xcc 0xcc
```

FOC返回的速度和发到Dash显示的速度是不同的，因为FOC理论上只知道换相速度，实际的行驶速度和电机极对数，电机轮径有关系。所以有个换算关系，这里运行脚本`utils/find_speed.py`列一下实际抓到的数据对，也就是FOC返回的速度和发到仪表的速度的对应关系

```
>>> {0: 0, 3: 1, 4: 1, 5: 2, 7: 3, 10: 4, 13: 6, 14: 6, 16: 7, 17: 8, 21: 10, 23: 11, 24: 11, 25: 12, 30: 14, 31: 14}
```

从这些数据可以大致推测，算法可能是`dash_speed = foc_speed * 12 // 25`

## 自制中控探讨

虽然很多数据帧的格式没有完全搞明白，但是关键的部分应该都有了。我想已经可以自制一些极大简化版的部件了。例如应该可以自制中控，自制仪表，自制电池通信，自制控制器通信了。在小牛车上，以上任何一个部件故障，都会极大影响体验。例如电池无法通信，居然会无法切换挡位，难道真的是为了电池安全考虑么？感觉有点类似电动汽车娱乐屏死机，导致油门加不上去。但是我个人认为，对于牛店，也包括其他的电动车店来说，想办法让用户去店里永远是挣钱的第一步。

我买了点485芯片，也有闲置的单片机，下一步就是看看能不能做个简易中控，这个简易中控的唯一的作用就是激活电机控制器，使得可以切换挡位，这样才能正常骑行，也可以用其他电池了。电量显示速度显示什么的，不看也能开。
